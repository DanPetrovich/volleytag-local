# VolleyTag

VolleyTag — локальный computer-vision конвейер для персонального анализа
волейбольного видео. Система строится вокруг конкретного игрока: находит его на
новых матчах, собирает непрерывную временную траекторию, связывает её с мячом,
позой и игровым контекстом и готовит проверяемые кандидаты действий и касаний.

Это уже не просто ручной разметчик статистики. В репозитории есть полный
исследовательский цикл: специализированные YOLO-детекторы, подготовка и аудит
датасетов, DINOv2-reranking, temporal routing, детектор мяча, разметка точного
контакта, позиционные priors, frozen/untouched evaluation и отдельные интерфейсы
human review. Старый интерфейс кнопочной и голосовой разметки сохранён как
вспомогательный инструмент и безопасный ручной fallback.

## Текущий статус

| Компонент | Состояние |
| --- | --- |
| Персональный детектор игрока | Рабочий источник кандидатов; v9 показывает 92,86% top-1 на отдельном непрерывном KEAZ test split |
| Candidate reranker | RBF-SVM v3: 82,98% micro top-1 на leave-one-whole-source-out, +8,09 п.п. к v2 |
| Temporal route | На untouched матче top-1 вырос с 73,72% до 79,20%, ошибок стало меньше на 20,83% |
| Детектор мяча | Untouched test: 90,00% recall положительных кадров и 92,31% specificity отрицательных |
| Точный контакт и действие | Активный R&D: признаки уже полезны, но полностью автоматическая статистика пока не заявляется готовой |
| Границы розыгрыша | Audio 8/мин + grouping 2 с: 32/34 training serve-anchor при ≈5,46 кандидата/мин; sparse visual head не прошёл непрерывный критерий |
| Human review и evaluation | Рабочие интерфейсы, независимый GT, uniform sampling, validated gaps и frozen-протоколы |

Temporal route v12 улучшил все основные метрики, но формально не достиг
заранее заданного порога снижения ошибок в 25%, поэтому не объявлен основной
моделью. Такая строгость намеренная: удачный отдельный прогон не превращается в
«production» задним числом. Полная история решений и точные протоколы находятся
в [`docs/experiment-results-2026-11-05.md`](docs/experiment-results-2026-11-05.md).

## Что входит в систему

- персональная детекция игрока на ближнем и дальнем ракурсах;
- generic person tracking и объединение кандидатов без доверия одному `track_id`;
- DINOv2 embeddings и lightweight reranker для сложных одноклубников;
- temporal decoder с motion gate, короткими bridge-интервалами и явным состоянием `missing`;
- специализированный детектор мяча и признаки траектории, близости, пересечения и позы;
- детекция полноэкранных broadcast-заставок и исключение интервалов повторов;
- разметка действий, точного контакта, ротаций, позиционного цикла и геометрии площадки;
- аудит боксов, hard negatives, domain balance и очистка персонального датасета;
- отдельные training, calibration, error-set, frozen и untouched контуры;
- локальные review-интерфейсы и byte-range server для больших видео;
- приватные Kaggle kernels для тяжёлого обучения и оценки;
- лёгкие regression-тесты и GitHub Actions.

## Архитектура

```text
локальное видео
      │
      ├── generic person detector / tracking ───────┐
      ├── персональный YOLO detector ───────────────┤
      └── human anchors / corrections ──────────────┤
                                                    ↓
                              candidate fusion + DINOv2 reranker
                                                    ↓
                                  temporal route / missing state
                                                    ↓
                         непрерывная траектория конкретного игрока
                                                    │
                     ┌──────────────────────────────┼───────────────┐
                     ↓                              ↓               ↓
              детектор мяча                  pose / geometry   rotation priors
                     └──────────────────────────────┼───────────────┘
                                                    ↓
                                  кандидаты контактов и действий
                                                    ↓
                         human review → frozen evaluation → отчёт
```

Видео, кадры, веса, embeddings, приватные реестры матчей и приватные экспорты
разметки не публикуются в Git. Репозиторий содержит воспроизводимый код,
конфигурации приватных kernels, тесты и компактные агрегированные отчёты.

## Локальные интерфейсы

Для запуска review-интерфейсов и вспомогательного ручного разметчика нужен
Python 3; внешние пакеты серверу не требуются.

```bash
git clone https://github.com/DanPetrovich/volleytag-local.git
cd volleytag-local
chmod +x start.command
./start.command
```

Можно просто дважды нажать `start.command` в Finder. Окно Terminal должно оставаться открытым. Для остановки нажми `Ctrl+C`.

После запуска главная страница открывает сохранённый ручной fallback. Ссылка
**«Трекинг игрока»** ведёт в основной review-интерфейс идентификации. Остальные
специализированные экраны собраны в каталоге `web/`:

- `web/tracking-review.html` — training/evaluation/uniform GT для игрока;
- `web/dataset-audit.html` — аудит персонального датасета;
- `web/action-review.html` — разметка игровых действий;
- `web/exact-contact-review.html` — покадровая разметка момента касания;
- `web/whistle-review.html` — проверка аудиокандидатов начала и конца розыгрыша;
- `web/rally-state-review.html` — визуальная разметка подготовки к подаче,
  активного розыгрыша и паузы между розыгрышами без подсказки аудиодорожки;
- `web/referee-calibration.html` — одноразовое выделение первого судьи для
  последующей разметки разрешения подачи и жеста окончания очка;
- `web/referee-gesture-review.html` — увеличенная source-balanced проверка
  разрешения подачи, окончания очка и других жестов первого судьи;
- `web/court-calibration.html` — геометрия площадки и зон;
- `web/rotation-review.html` и `web/position-cycle-review.html` — ротации и цикл 5–1.

В ручном fallback:

1. Перетащи видео в большую область плеера или нажми «Выбрать файл».
2. Короткое нажатие `Space` включает или останавливает видео.
3. Удержание `Space` записывает голосовую отметку.
4. Буквы на кнопках работают как горячие клавиши, `←`/`→` перематывают на 5 секунд.

Ручной запуск на другом порту:

```bash
python3 range_server.py 8765
```

Затем открой <http://127.0.0.1:8765>.

## Ручная и голосовая разметка

Первоначальный интерфейс ручной статистики остаётся доступен на `web/index.html`.
Он размечает приём, атаку, подачу, блок и защиту, считает базовые показатели,
экспортирует CSV/JSON и умеет отправлять результат в Google Sheets. Голосовой
режим использует Groq Whisper и текстовую модель только как опциональный ввод;
без API-ключа кнопочная разметка продолжает работать локально.

Подробная настройка fallback-интерфейса, Groq и Google Sheets вынесена в
[`docs/manual-tagger.md`](docs/manual-tagger.md), чтобы не смешивать её с
основным CV-конвейером.

## Что хранится в Git

В репозиторий входят исходники интерфейсов, скрипты подготовки данных, обучения и
оценки, тесты, Kaggle kernel-конфигурации и компактные отчёты. Тяжёлые и/или
приватные артефакты остаются вне Git:

- исходные видео и извлечённые кадры;
- `vision/runs/`, локальные `runs/` Ultralytics и candidate caches;
- веса `.pt`, embeddings `.npy` и обученные lightweight-heads `.joblib`;
- пользовательские экспорты разметки и локальные ключи.

Kaggle datasets и kernels для обучения создаются приватными. Замороженные
тестовые матчи нельзя использовать для обучения, выбора эпохи, порогов или
маршрута.

## Персональный CV-конвейер

### Интерактивное подтверждение игрока

После запуска `start.command` открой ссылку **«Трекинг игрока»** в верхней панели. На отдельном
экране можно загрузить исходное видео, `tracking/tracks.csv` и необязательный
`reid/similarity.csv`. Первый клик только показывает кандидата фиолетовой рамкой. Если в одной
точке наложилось несколько рамок, повторные клики перебирают их; отдельная кнопка подтверждает
«это игрок №51». Для точного выбора есть шаг ±0,1 секунды и полноэкранный режим. Ошибочный якорь
можно отменить. Система продолжает выбранный трек между розыгрышами, при потере ставит видео на паузу и ждёт следующего подтверждения.

Новое подтверждение в уже размеченном месте является коррекцией: оно заменяет прежнюю рамку с
этого момента. Сопровождение считается покадрово по положению, скорости и размеру игрока, а не
по одному `track_id`; дублирующие рамки детектора перед показом схлопываются. Между двумя
подтверждениями траектория строится с обеих сторон и в каждой точке использует ближайший якорь.
Все подтверждённые `track_id` дополнительно считаются положительными кандидатами.

### Разметка персонального датасета

Разметчик сохраняет не отдельные кадры, а временные интервалы. Поэтому весь матч не нужно
прокликивать покадрово:

- **Q** — выбранная рамка принадлежит игроку №51; начинается положительный интервал;
- **W** — текущая рамка принадлежит другому человеку; интервал закрывается и сохраняется
  сложный отрицательный пример;
- **E** — игрока сейчас не видно или детектор не создал рамку;
- **Пробел** — пауза/воспроизведение, стрелки — переход на 5 секунд.

Ракурс определяется автоматически по положению рамки и записывается отдельно как
`near_back` (ближняя сторона, спиной) или `far_front` (дальняя сторона, лицом). Перед Q его
можно исправить вручную в списке «Ракурс». Это позволяет обучать два классификатора поверх
общего визуального энкодера, не смешивая принципиально разные изображения игрока.

Кнопка **W** сохраняет текущий фрагмент как отрицательный пример. Если вместо неё сразу выбрать
и подтвердить правильную рамку, ошибочный кандидат также записывается автоматически. Экспорт
`player-51-training-data.json` содержит интервалы, ракурсы, подтверждённые ветки маршрута,
отрицательные примеры и моменты потери. Черновик автоматически хранится только в браузере.

Из обратной связи можно собрать персональный профиль и глобальный маршрут:

```bash
.venv-vision/bin/python vision/build_feedback_profile.py VIDEO TRACKS FEEDBACK \
  --output vision/runs/feedback-profile

.venv-vision/bin/python vision/optimize_feedback_route.py VIDEO TRACKS FEEDBACK \
  vision/runs/feedback-profile/chunk_similarity.csv \
  --output vision/runs/feedback-route
```

Первый скрипт вырезает несколько ракурсов вокруг каждого клика, строит OSNet-профиль и отдельно
оценивает каждый непрерывный фрагмент. Второй ищет согласованную траекторию по всему видео;
подтверждения являются жёсткими точками, а фрагменты «не я» исключаются.
Подтверждения хранятся локально в браузере и экспортируются в `player-51-anchors.json`.

Для длинного непрерывного фрагмента сначала подготовь рамки:

```bash
.venv-vision/bin/python vision/run_player51_pilot.py /путь/к/фрагменту.mp4 \
  --output vision/runs/review-fragment \
  --profile models/player51-multiview.npz \
  --detector-imgsz 1536 \
  --detector-conf 0.08
```

Отсутствие OCR-якоря и статус `needs_review` здесь нормальны: интерактивный экран как раз нужен,
чтобы задать якоря кликами. Для видео 1920×1080 оставь ROI X/Y равными 40/70. Это пилот
человека-в-контуре: рамки создаёт YOLO, пользователь только подтверждает личность.

### Один автономный запуск

Готовый пилот объединяет три сигнала: OCR номера даёт подтверждённый якорь, OSNet ReID
ранжирует визуально похожие фрагменты, а геометрия траектории склеивает соседние временные ID.
После установки зависимостей весь процесс запускается одной командой:

```bash
.venv-vision/bin/python vision/run_player51_pilot.py /путь/к/матчу.mp4 \
  --output vision/runs/my-match \
  --profile models/player51-multiview.npz
```

Главный результат лежит в `my-match/fused/fused-51.mp4`, машинный отчёт — в
`my-match/report.json`. Если номер ни разу не подтверждён, программа ставит
`fusion_status: needs_review` и сохраняет `reid/candidates.jpg`, но намеренно не рисует
«уверенную» рамку по одному ReID. На одинаковой форме это важная защита от ложного игрока.

Если игрок далеко от камеры, обычный размер детекции может пропустить его полностью. Для такого
розыгрыша можно повысить детализацию, уменьшить порог и после просмотра `tracking/tracked.mp4`
подтвердить один непрерывный кусок в формате `ID:CHUNK`:

```bash
.venv-vision/bin/python vision/run_player51_pilot.py rally.mp4 \
  --output vision/runs/serve-rally \
  --profile models/player51-multiview.npz \
  --detector-imgsz 1536 \
  --detector-conf 0.08 \
  --seed-segments 25:0,157:0 \
  --min-continuation-margin 0.0
```

Номер chunk можно сопоставить с временным ID по `fused/chunks.csv`; этот файл создаётся и при
первом запуске без якоря, когда программа останавливается на `needs_review`. Ручной seed
относится только к одному непрерывному куску,
а не ко всему глобальному ID: трекер иногда повторно использует ID после пропуска. После seed
геометрическая сшивка выбирает одну непрерывную ветку и не выводит одновременно несколько
перекрывающихся боксов. Продолжение с отрицательным ReID margin отклоняется: безопаснее временно
не показывать рамку, чем переключиться на другого человека. Это полуавтоматический режим, а не
автоматическое распознавание подачи.

Файл профиля персонален и исключён из Git. Его можно собрать из уже проверенных временных ID:

```bash
.venv-vision/bin/python vision/identify_player.py match.mp4 vision/runs/test/tracks.csv \
  --seed-ids 7,249,261 \
  --negative-ids 2,4,5,40,125 \
  --save-profile models/player51-multiview.npz \
  --output vision/runs/profile-build
```

Добавлять новые подтверждённые ракурсы можно повторным запуском одновременно с `--profile` и
`--save-profile`. Практический аудит пилота и известные ограничения собраны в
[`vision/PILOT_REPORT.md`](vision/PILOT_REPORT.md).

Для воспроизводимой проверки используются только границы настоящих розыгрышей из Balltime, а не
случайные тайм-коды. Размеченный top-5 трёх независимых rally можно пересчитать командой:

```bash
.venv-vision/bin/python vision/evaluate_balltime_rallies.py
```

Текущий результат: правильный кандидат находится на первом месте в 2 из 3 розыгрышей и входит в
первые два во всех 3 из 3. Это оценка ранжирования фрагментов, не покадровая точность.

В `vision/track_players.py` лежит первый автономный этап будущего поиска игрока №51. Он:

- находит людей моделью YOLO11;
- связывает detections во временные треки через BoT-SORT с визуальным ReID;
- сохраняет видео с временными ID;
- пишет все рамки и таймкоды в `tracks.csv`;
- собирает `tracks.jpg` с лучшим кадром каждого ID.

На дальней стороне игрок занимает мало пикселей, поэтому для неё предусмотрен отдельный
увеличенный проход. Он добавляется к исходным рамкам, не меняя старые ID и уже сделанную
разметку:

```bash
.venv-vision/bin/python vision/track_players.py vision/runs/training-set2/source.mp4 \
  --output vision/runs/training-set2/far-tracking \
  --roi 40,70,1900,600 --stride 2 --imgsz 1536 --conf 0.05

.venv-vision/bin/python vision/merge_multizone_tracks.py \
  vision/runs/training-set2/tracking/tracks.csv \
  vision/runs/training-set2/far-tracking/tracks.csv \
  vision/runs/training-set2/tracking/tracks.csv --backup
```

Светло-оранжевые кроссовки №51 можно посчитать как дополнительный положительный признак:

```bash
.venv-vision/bin/python vision/score_shoe_color.py \
  vision/runs/training-set2/source.mp4 \
  vision/runs/training-set2/tracking/tracks.csv \
  --output vision/runs/training-set2/shoe-scores.csv
```

Файл подключается к `optimize_feedback_route.py` через `--shoe-scores`. Нулевой результат
нейтрален: если обувь закрыта или размыта, это не считается доказательством «не №51».

Это пока не распознавание конкретного человека. В спортивном видео трек часто рвётся после
перекрытия или поворота: один игрок может получить несколько ID. Следующий этап — объединить
такие куски по визуальному сходству (ReID) и редким кадрам, на которых читается номер 51.

Для этого второго этапа есть `vision/identify_player.py`. Ему передаются подтверждённые
временные ID игрока и, желательно, несколько ID других игроков той же команды. Скрипт строит
локальный профиль внешности OSNet, ранжирует остальные треки и создаёт видео только с выбранным
игроком:

```bash
.venv-vision/bin/python vision/identify_player.py match.mp4 vision/runs/test/tracks.csv \
  --seed-ids 14,70,92 \
  --negative-ids 6,11,56 \
  --output vision/runs/player-51
```

Результаты включают `similarity.csv`, лист кандидатов и `player-51.mp4`. Один референс обычно
недостаточен: на дальней камере OSNet прежде всего видит одинаковую форму. Несколько ракурсов,
отрицательные примеры и читаемый номер заметно повышают точность; окончательное подтверждение
кандидатов пока остаётся ручным.

Если номер на спине читается, `vision/detect_jersey_number.py` использует его как более сильный
сигнал. Скрипт вырезает центральную часть майки, локально запускает Tesseract и принимает номер
только после нескольких совпадений внутри одного временного трека:

```bash
brew install tesseract
.venv-vision/bin/python vision/detect_jersey_number.py match.mp4 \
  vision/runs/test/tracks.csv --target 51 --output vision/runs/number-51
```

OCR запускается покадрово и пока медленный. Это экспериментальный источник подтверждений для
ReID, а не готовый распознаватель всех номеров: поворот лицом, смаз и перекрытия снижают recall.

`vision/fuse_player_signals.py` превращает редкие OCR-попадания в непрерывное сопровождение:
надёжный номер создаёт якорь, а разорванные треки соединяются по времени и траектории. Глобальный
ID трекера сначала режется на непрерывные куски при пропуске наблюдений: поэтому ID-switch после
перекрытия не распространяет OCR-подтверждение на другого игрока:

```bash
.venv-vision/bin/python vision/fuse_player_signals.py match.mp4 \
  vision/runs/test/tracks.csv vision/runs/number-51/ocr.csv \
  --similarity vision/runs/player-51/similarity.csv \
  --target 51 --output vision/runs/fused-51 \
  --seed-segments 25:0
```

Установка в отдельное окружение:

```bash
python3 -m venv .venv-vision
.venv-vision/bin/python -m pip install -r vision/requirements.txt
```

Пробный запуск на первых 60 секундах видео:

```bash
.venv-vision/bin/python vision/track_players.py /путь/к/матчу.mp4 \
  --output vision/runs/test \
  --max-seconds 60 \
  --stride 3 \
  --roi 40,70,1900,1020
```

`--device auto` сначала пробует Metal/MPS на Apple Silicon, затем использует CPU. Чем меньше
`--stride`, тем надёжнее трекинг и дольше обработка. Координаты `--roi` подходят только для
тестового видео 1920×1080; для другой камеры их нужно изменить или убрать параметр.

Конфигурация `vision/botsort_reid.yaml` хранит потерянный трек до 90 обработанных кадров,
отключает ненужную для статичной камеры компенсацию движения и сравнивает визуальные признаки
игроков. На одном и том же 17-секундном Rally #46 обычный BoT-SORT создал 105 временных треков,
а режим с ReID — 90. Это уменьшает фрагментацию примерно на 14%, но не заменяет отдельную
идентификацию номера 51: одинаковая форма одноклубников остаётся сложным случаем.

На MacBook Pro M3 Pro тестовый 30-секундный фрагмент при `stride=5`, `imgsz=960` и CPU был
обработан за 26,4 секунды — 1,14× быстрее длительности исходника. При этом 51 временный ID
показывает, что детекция уже работает, а объединение разорванных треков действительно необходимо.

Ultralytics распространяется отдельно и имеет собственные лицензионные условия. Перед
коммерческим использованием нужно проверить актуальную лицензию зависимости.

## Evaluation mode для замороженного теста

`web/tracking-review.html` сохраняет прежний режим `Training / review v3` и его экспорт
`player-51-training-data.json`. Для независимой разметки тестового видео выбери
`Evaluation v4 (замороженный тест)`. Этот режим экспортирует схему
`volleytag.player51-evaluation.v4` и не превращает `uncertain` в положительный или
отрицательный пример.

Рабочий цикл evaluation mode:

1. Выбери подтверждённый человеком ракурс `near_back` или `far_front`.
2. Клавишами `1`–`4` начни следующий интервал `visible`, `occluded`,
   `out_of_frame` или `uncertain`; новый интервал закрывает предыдущий.
3. `Q` добавляет выбранную рамку как human GT keyframe, `R` позволяет нарисовать
   независимую GT-рамку. После `Q` интерфейс также строит вспомогательное сопровождение
   для удобства разметки; оно не экспортируется как prediction и не участвует в метриках.
   `G` начинает или завершает явный validated gap.
4. `B` начинает или завершает просмотренный диапазон. Границы всех диапазонов
   можно исправить числовыми полями в списке.
5. `W` записывает исправление identity/box с `error_start_s`, состояниями
   before/after и причиной.
6. Отметь `Review complete` только после 100% reviewed coverage и экспортируй JSON.

Экспорт блокируется при пересечении reviewed/presence-интервалов, неполном
coverage при `review.complete` и если `visible` не покрыт GT-траекторией или
явным validated gap. Хеши и commit добавляются только из введённых значений — UI
их не придумывает. Состояние обоих режимов хранится раздельно в `localStorage`;
JSON v3 и v4 можно импортировать для продолжения работы.

### Uniform test: репрезентативная оценка вместо журнала исправлений

`Uniform test v1` заранее выбирает кадры с постоянным шагом (по умолчанию две
секунды) и сохраняет их отдельно от training/review и Evaluation v4. Автоматический
зелёный маршрут в этом режиме отключён, чтобы prediction не подсказывал разметчику
ответ. На каждом кадре нужно либо выбрать/нарисовать GT-рамку, либо отметить
`occluded`, `out_of_frame` или `uncertain`. После ответа интерфейс сам переходит к
следующему фиксированному кадру. Черновик хранится под отдельным ключом в
`localStorage`, экспорт имеет схему `volleytag.player51-uniform-evaluation.v1`.

Пример локального URL:

```text
web/tracking-review.html?video=VIDEO&tracks=TRACKS&mode=uniform&step=2
```

Такой набор используется только как замороженный тест. Клики, сделанные во время
обычного просмотра после сбоя трекера, остаются отдельным error set и не заменяют
равномерную выборку.

Цвет обуви проверяется независимо от ReID-модели и без подбора порога на тесте:

```bash
.venv-vision/bin/python vision/evaluate_shoe_signal_gt.py VIDEO TRACKS UNIFORM_JSON \
  --output vision/runs/shoe-evaluation
```

Скрипт считает recall детектора, top-1/top-3 ранжирование только по оранжевому
сигналу, ROC AUC/AP среди всех найденных кандидатов и recall прежнего фиксированного
порога. Обувь является положительным вспомогательным сигналом: отсутствие цвета не
означает «не №51», потому что ноги могут быть закрыты или размыты.

Минимальная проверка схемы и интервалов:

```bash
node vision/tests/test_evaluation_schema.js
```

## Данные и приватность

- видео остаётся на компьютере;
- события хранятся в `localStorage` браузера;
- при голосовой разметке короткое аудио и текст отправляются выбранному AI-провайдеру;
- `.groq-key`, `config.local.js`, видео, экспорты и голосовые логи исключены из Git;
- для переноса событий используй резервную копию JSON.
